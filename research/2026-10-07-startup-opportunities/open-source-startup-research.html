Research snapshot • 7 October 2026 • Revenue and startup potential first

Where Evalcraft and Pactrun can become a business

Use the two existing projects to sell a narrowly scoped, tested business-action workflow. Start with refunds in custom support agents. Validate paid demand before building a third framework or expanding the platform.

The strongest near-term offer is a refund-workflow review and regression pack, followed by application-level controls and evidence for the exact customer workflow. Evalcraft can reproduce failures; Pactrun can enforce contracts at covered tool boundaries. This is a commercial hypothesis supported by technical fit and adjacent demand, not demonstrated product–market fit.

The distinction must be customer value, not an invented empty category. Refund policies, approval-bound execution, replay testing, and evidence conformance already exist. Winning requires quicker integration with a customer's real business state, clear limits, repeatable tests, and enough operational value to earn a recurring contract.

Evalcraft: narrow the promise around reproducible code regressions

Evalcraft already has more than a simple replay helper: capture, cassette-only assertions, adapters, live evaluation, a dashboard/cloud area, and a source-only JavaScript SDK. Adding a generic dashboard, more common metrics, or “a JavaScript SDK” would duplicate existing effort or enter crowded categories. Its more useful story is: take one observed failure, run changed application code against recorded model replies, and explain what changed.

Replay and playback are different. Replay emits saved events; it does not execute the changed agent. Playback runs current code with recorded model responses and checks matching requests. Current playback covers non-streaming OpenAI Chat Completions and Anthropic Messages, sync and async; Responses API and streaming are explicitly refused. That refusal is a good boundary. A changed prompt that no longer matches the recording needs a fresh recording or live evaluation; offline playback cannot establish the quality of new model answers. See playback PR #29 and the local evalcraft/playback/player.py.

The observed distribution is uneven: local package 0.13.0, public main 0.12.0, and the PyPI page showed 0.11.0 during this research. The playback PR was still open. Do not advertise the local checkout as the default installed user experience. Release alignment belongs with the release/DevOps owner; no release automation was changed.

The Gemini adapter still targets google-generativeai. Google's official library guidance identifies that as a deprecated legacy SDK and recommends google-genai. Modernization is more useful than adding another adjacent metric. The contributing guide also contains a stale flat-file layout. Fixing the first-run experience, documentation map, and one current integration helps adoption more directly than increasing feature count.

Pactrun: turn honest limits into explicit, tested coverage

The code has meaningful runtime interception, particularly at MCP tool calls, rather than only offline scoring. Its limitations document correctly states that uncovered calls and external side effects are invisible, most adapters need host-supplied tool results/trust metadata for richer checks, and a plain hash chain can be rewritten. These limits should remain visible in product claims.

Three probes against local fake calls found gaps that matter before selling stronger guarantees. No SDK credentials, network requests, or real side effects were involved. The reproduction script accompanies this report.

5. The recommended offer and smallest useful product

Offer hypothesis: “Before you enable autonomous refunds, we test your agent against your refund rules, reproduce failures, and help enforce the rules at the actual refund tool.”
Start with one workflow, one customer backend, and one supported framework.

Initial customer: a product team building a custom customer-support/commerce agent, or a vendor shipping such agents to other companies. They own the refund endpoint and have a specific launch blocker, incident, or expensive review process. The likely initial buyer is an engineering lead, AI product lead, or founder. The workflow owner helps define the policy. This is an intended customer profile to test, not a measured customer segment.

The first qualifying question is: “What action have you delayed enabling because you cannot confidently verify it follows your business rules?” Ask for a recent incident or failed scenario, current test/control implementation, who approves the rollout, and what they would buy instead. Teams with FAQ-only agents, no write actions, no access to tool code, or no budget owner are weak initial prospects.

One refund journey with measurable acceptance cases

  1. Read authoritative customer/order state through application-owned code. Carry authenticated tenant and customer identity; do not let model-supplied IDs establish ownership.
  2. Validate currency, minor-unit amount, order ownership, remaining refundable amount, and the business rule version. Compare an explicit action proposal with current state.
  3. Where approval is required, bind it to the exact action and context. Recheck relevant state at commit time; changed amount, tenant, recipient, or policy must invalidate an old grant.
  4. Reserve an action/grant atomically, use the provider's idempotency facility where available, and reconcile uncertain results after a timeout. Treat “unknown outcome” as distinct from success or safe-to-retry.
  5. Record decision, attempted execution, observed provider result, and the final outcome evidence. Redact/limit sensitive fields and state which facts were independently observed.
  6. Use Evalcraft to reproduce the incident and rerun changed application code. Use Pactrun at the covered tool boundary. Export results to the customer's existing tracing system instead of replacing it.

This is a proposed architecture. It is not already guaranteed by either project. A consumed grant does not itself guarantee exactly-once external payment execution; real provider idempotency, atomic application state transitions, and outcome reconciliation are needed. An SDK cannot authorize an endpoint that the agent can reach through an uncovered route. Testing known cases is evidence of those cases, not universal proof of safety.

The existing tau2-bench is relevant for support-agent domain evaluation. Application backlog, in the right order

  1. Clarify and test coverage. Publish supported call paths and enforcement timing. Fix or refuse the silent Responses pass-through. Add targeted concurrency and approval tests that reproduce the findings.
  2. Harden the approval/action lifecycle. Full-context authenticated grants, explicit identity source, single-use state, reservation/reconciliation, and restart tests. Start with a simple application-owned storage interface; choose backend needs with the pilot customer.
  3. Build a small Evalcraft–Pactrun bridge. Normalize token semantics and stable action identity; map cassette tool events and results to policy events; preserve unknown/unobserved fields rather than fabricate trust or approval.
  4. Ship one synthetic refund example. Fake stateful tools, deterministic failure cases, and no API keys. Separate current-code playback from checking a saved event sequence. Add one requested framework integration, not six speculative ones.
  5. Improve installation and contributor onboarding. Current documentation paths and Gemini SDK migration where customers need it. Hand package/release alignment to the responsible release team.
  6. Only after paid usage repeats, add team workflow features. Private policy review, approval evidence retention, versioned workflow comparisons, and support agreements. Do not build another dashboard before learning what buyers repeatedly need.

All of this is proposed application work. No repository source, cassette, golden fixture, CI/workflow, shell script, Docker, infrastructure, deployment, or release automation was changed during research. New synthetic test cases can be authored with clear provenance; existing recorded baselines must not be edited to make a failure pass.

Pricing and the path from service revenue to a startup

Test price, not forecast: offer a fixed two-week pilot at $1,500–$3,000 for one workflow, one supported integration, a reviewed failure set, an executable regression pack, and a practical control-boundary report. Agree acceptance criteria before starting. A recurring $300–$1,000/month offer is a later experiment for policy-change review, regression maintenance, and team evidence workflows—not an assumed conversion.

At an illustrative $2,000 pilot and 20 founder-hours, revenue is $100 per delivery hour before acquisition, support, tooling, and other costs. Ten customers at $500/month would be $5,000 MRR: useful validation, but not proof of a scalable venture. If every customer needs a custom engine or extensive consulting, this remains a service business. Seek repeated integrations and expanding workflow coverage before investing in a hosted product.

Potential defensibility is accumulated workflow knowledge, trustworthy integration behavior, and customer adoption—not predicate count. Learn whether multiple customers share the same refund-state and reconciliation model. If a few agent vendors can reuse your pack across their own customers, distribution and contract size may improve. That remains an inference to validate; no TAM, fundraising outcome, or revenue projection is asserted.

Open source should keep the core checks, local tests, and integration points usable. Paid value can come from setup, maintained private workflow suites, organization review processes, and support. Enforra already describes a similar optional cloud boundary, so this packaging alone is not differentiation. The offer must save the buyer measurable engineering/review time or unblock a specific safe action.

6. How to attract contributors without confusing it with revenue

Contributor growth needs a contribution someone can finish and use. A feature-rich engine maintained mostly by its author does not offer an obvious first task. Make contribution units small: a synthetic failure case, one framework hook, a clear unsupported-path check, or a real normalization bug with a reproducer.

As a directional check, samples of the most recently updated closed PRs showed multiple author accounts in established projects: Langfuse 10 across 30 sampled PRs, DeepEval 7 across 30, and Agent Control 6 across 30. Evalcraft had 2 across its 8 sampled closed PRs; Pactrun had 1 across its single closed PR. These are sampled author-account counts, not verified humans, outside contributors, 30-day activity, or total contributor counts; employees and automation may be included. GitHub stars also do not measure retention or purchase intent.

The proposed name is a working label; availability was not checked. The repository would contain small, engine-neutral executable support-workflow cases and fake stateful tools. It would not introduce another runner, normative standard, or policy language. Reuse pytest and existing engines. A concrete first contributor backlog

  • A fake refund case for different tenant identity despite a matching order ID.
  • A grant whose amount changes after approval, with an unchanged-action control case.
  • A provider timeout after accepting the action, followed by reconciliation.
  • Two concurrent attempts for one action, with stable, inspectable outcomes.
  • A current Responses API supported/refused-path test and documentation entry.
  • A cache-token normalization example between the projects.
  • One community-requested framework binding that observes results as well as proposed tool calls.
  • An ACS/Probity compatibility adapter coordinated with the active upstream work.

Publish scope, prerequisites, expected outputs, and a reviewer for each task. Design the smallest examples to run locally without keys in under 15 minutes; time that claim before publishing it. Review useful first PRs promptly and explain rejections. A contributor should be able to retain value from a case or adapter even without adopting both libraries.

For distribution, use a working demo with one reproduced incident, a before/after decision diff, and an honest coverage statement. Seek relevant integrations and maintainer discussions when explicitly authorized. Broad star campaigns, repetitive issue comments, and inflated safety claims will not establish a useful community. No external outreach was sent during this research.

Measure independent organizations using the examples, merged outside-account contributions, repeat contributions, time to first successful case, and maintenance burden. Keep leads/pilots/revenue separate from these measures. A planning target such as five outside-account merged PRs in 90 days is a goal to test, not a prediction or a proxy for product–market fit.

9. Research scope, limitations, and saved evidence

This research inspected the two local projects' documentation, application code, package metadata, history, and tests; reviewed public repository metadata and selected issues/PRs; and checked primary product documentation and pricing. Competitor comparisons are documentation-based unless stated otherwise. Third-party suites were not run, private customer deployments were not inspected, and there were no buyer interviews during this research.

The repository selection is purposive and not exhaustive. Search visibility and public issues favor technical teams and public failures.
